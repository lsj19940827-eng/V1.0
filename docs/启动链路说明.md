# 启动链路说明

更新日期：2026-05-13

本文只回答一个问题：从执行 `main.py` 到用户看到主窗口，这个程序现在到底经过了哪些明确分层。

关联文档：
- [项目总览](./项目总览.md)
- [模块依赖地图](./模块依赖地图.md)
- [高风险文件清单](./高风险文件清单.md)

## 1. 启动总览

当前最短路径是：

`main.py` -> `app_渠系计算前端/bootstrap.py` -> 启动环境兼容保护 -> 授权校验 -> `Qt WebEngine` 预检/应急模式 -> `StartupContext` -> `MainWindow` -> `PanelRegistry` -> `ProjectManager` -> 静默更新检查

```mermaid
flowchart TD
    A[main.py main()] --> B[插入仓库根目录到 sys.path]
    B --> C[调用 bootstrap.run()]
    C --> D[初始化环境、High DPI 与 platform WMI 保护]
    D --> E[ensure_qfluentwidgets_compat]
    E --> F[license_checker.check_license()]
    F -->|失败| X[退出 code 1]
    F -->|通过| G[Qt WebEngine 标准预检或隐藏应急模式]
    G -->|IPC 0x5 拒绝访问| C1[自动切换单进程兼容模式]
    G -->|其他失败| Y[显示诊断并退出 code 2]
    G -->|通过| H[创建 QApplication]
    C1 --> H
    H --> I[构造 StartupContext]
    I --> J[构造 MainWindow]
    J --> K[创建运行时 manager]
    K --> L[构造 PanelRegistry 并只创建首屏面板]
    L --> M[ProjectManager.bind_runtime]
    M --> N[显示主窗口]
    N --> O[启动静默更新检查]
    O --> P[进入事件循环]
```

## 2. 第 1 段：`main.py` 只保留极简入口职责

主入口在 [../main.py](../main.py)。它现在只做两件事：

- 把仓库根目录加入 `sys.path`
- 调用 [../app_渠系计算前端/bootstrap.py](../app_渠系计算前端/bootstrap.py) 的 `run()`

如果 `bootstrap.run()` 抛异常：

- `main.py` 会打印异常栈
- 在非 frozen 环境下等待一次回车，便于本地排错
- 最终 `sys.exit(1)`

这意味着 `main.py` 已经不再承担授权、WebEngine 预检、`QApplication` 创建等细节，它只是脚本入口壳。

## 3. 第 2 段：`bootstrap.py` 是唯一启动编排层

[../app_渠系计算前端/bootstrap.py](../app_渠系计算前端/bootstrap.py) 现在负责所有启动阶段的全局决策，顺序固定为：

1. `initialize_runtime_environment()`：设置 `QT_ENABLE_HIGHDPI_SCALING`、高 DPI rounding policy，并禁用 Python `platform` 的 Windows WMI 快速路径
2. `ensure_qfluentwidgets_compat()`：安装 `darkdetect` 超时保护
3. `_check_license()`：调用 [../license_checker.py](../license_checker.py)
4. `build_startup_context()`：执行 Qt WebEngine 标准预检；父进程不提前导入 WebEngine，明确检测到 Windows IPC `0x5` 拒绝访问时自动启用单进程兼容模式
5. `ensure_application()`：创建并统一配置 `QApplication`、字体、全局样式和 Matplotlib DPI；禁用临时窗口触发的隐式退出并清理遗留退出事件
6. 构造 [../app_渠系计算前端/app.py](../app_渠系计算前端/app.py) 的 `MainWindow`
7. 根据启动参数决定是否立即弹更新对话框
8. 显示主窗口并启动静默更新检查

这里最重要的变化是：

- Qt WebEngine 的真因诊断只保留在 bootstrap，不再散落在 `MainWindow` 或业务 panel 中
- Qt WebEngine 标准预检会给首次冷启动保留 20 秒外层预算；输出改由临时文件承接，避免 Chromium 孤儿子进程继承 PIPE 后让父进程继续假死
- 预检明确出现 Windows IPC `0x5` 拒绝访问时会自动切换兼容模式；导入失败、文件缺失和其他未知故障仍保持诊断阻断
- 兼容参数必须在父进程首次导入 `QtWebEngineWidgets` 之前写入；模块可用性检查只读取导入规格，真实导入仍由探测子进程执行
- 主程序不依赖 Qt 的“最后窗口关闭”隐式规则；只有 `MainWindow.closeEvent()` 接受关闭后才显式退出，防止启动期临时窗口让主界面刚显示就消失
- 包初始化 [../app_渠系计算前端/__init__.py](../app_渠系计算前端/__init__.py) 不再有 import-time 副作用
- `StartupContext` 成为主窗口读取运行时事实的唯一入口
- Windows 下第三方库导入阶段若读取 `platform.machine()`，会走非 WMI 回退路径，避免本机 WMI 卡住时把主窗口阻塞在面板装配前

## 4. 第 3 段：`MainWindow` 只负责 UI 装配

主窗口在 [../app_渠系计算前端/app.py](../app_渠系计算前端/app.py) 中，入口签名已经收口为 `MainWindow(startup_context)`。

主窗口初始化时会完成：

- 标题、图标和尺寸设置
- 创建运行时 `SiphonManager` 与 `PressurePipeManager`
- 构造 `PanelRegistry`
- 创建导航栏和 `QStackedWidget`
- 为全部模块建立稳定 `stack` 占位，启动时只实例化首屏“明渠设计”
- 初始化 `ProjectManager`
- 快捷键绑定
- 默认切换到第一个页面
- 根据 `StartupContext` 提示是否启用了 WebEngine 应急单进程模式

### 4.1 `PanelRegistry` 的职责

[../app_渠系计算前端/panel_registry.py](../app_渠系计算前端/panel_registry.py) 引入了两个核心类型：

- `PanelDescriptor`：描述一个面板的 `key`、标题、导航顺序、兼容属性名、工程序列槽位和工厂函数
- `PanelRegistry`：负责按需创建/缓存面板，并暴露统一查询接口

当前已启用真实懒加载。启动时只创建 `open_channel`；其余面板在用户首次点击导航、访问旧兼容属性，或 `ProjectManager` 恢复项目数据时创建。`PanelRegistry.instance_created` 会把新面板挂入预留栈位并接上脏状态信号。

### 4.2 旧属性名兼容仍然保留

虽然面板装配改成了注册表驱动，但这些访问入口仍然成立：

- `window.open_channel_panel`
- `window.aqueduct_panel`
- `window.tunnel_panel`
- `window.culvert_panel`
- `window.siphon_panel`
- `window.pressure_pipe_panel`
- `window.water_profile_panel`

这保证了现有测试和大部分内部调用不需要同步重写。

## 5. 第 4 段：`ProjectManager` 改为绑定运行时提供者

[../app_渠系计算前端/project_manager.py](../app_渠系计算前端/project_manager.py) 仍然是项目生命周期总控，但接线方式已经变化：

- 旧的 `set_panels(...)` 已移除
- 新的 `bind_runtime(panel_registry, services)` 统一接收面板提供者和 manager 服务

这带来的好处是：

- 保存、打开、自动保存和最近项目逻辑不再依赖一长串具体面板字段
- 面板脏状态连接通过 `PanelRegistry.instance_created` 统一挂接
- 项目文件格式 `.qxproj` 保持不变，但内部装配边界更清晰

当前仍由 `ProjectManager` 统一负责：

- 新建、打开、保存、另存为
- 自动保存
- 最近项目持久化
- 窗口标题中的项目名与脏状态
- `report_meta` 与 manager 数据的快照/回填

## 6. 第 5 段：更新系统在窗口显示后启动

更新相关逻辑仍然分成两层：

- [../app_渠系计算前端/update_dialog.py](../app_渠系计算前端/update_dialog.py)：更新对话框和静默检查线程
- [../updater.py](../updater.py)：版本检查、补丁/全量安装、回滚和会话恢复

与旧结构相比，变化点在于：

- `MainWindow` 不再在构造函数里自动拉起静默更新
- 启动编排层 `bootstrap.py` 会在 `window.show()` 之后调用 `window.start_silent_update_check()`
- 如果命令行带了更新参数，bootstrap 会先调用 `window.prepare_update_prompt(...)`，再由窗口打开对应的更新对话框

## 7. 启动链路里的关键协作对象

| 对象 | 主要职责 |
| --- | --- |
| `main.py` | 脚本入口壳、异常兜底 |
| `bootstrap.py` | 环境初始化、授权校验、WebEngine 预检、主窗口拉起 |
| `StartupContext` | 启动阶段事实快照 |
| `MainWindow` | 导航、面板装配、窗口级交互 |
| `PanelRegistry` | 面板描述、创建、缓存、兼容属性入口 |
| `ProjectManager` | 项目状态治理、保存/恢复、自动保存、最近项目 |
| `webengine_diagnostics.py` | 标准模式预检、诊断报告、隐藏应急模式 |
| `UpdateDialog` / `SilentUpdateChecker` | 更新 UI 与后台检查 |
| `updater.py` | 版本检查、安装会话与回滚 |

## 8. 启动链路中最容易忽略的事实

1. `app_渠系计算前端/__init__.py` 已不再自动执行 `ensure_qfluentwidgets_compat()`
2. Windows WMI 兼容保护发生在 bootstrap 的最早环境初始化阶段，早于 `qfluentwidgets`、`pandas` 和业务面板导入
3. WebEngine 启动决策发生在 bootstrap，而不是 `MainWindow`
4. 当前默认行为是首屏面板先创建，其余主面板按首次访问懒加载
5. `ProjectManager` 现在绑定的是注册表和服务，而不是一堆离散面板字段
6. 更新检查不再由窗口构造函数直接触发，而是由启动编排层在显示窗口后启动
7. 任务管理器可能优先识别无标题的 WebEngine 辅助窗口；验收应按主窗口标题枚举真实句柄，不能只读取 `MainWindowHandle`

## 9. 启动问题排查顺序

如果程序无法正常启动，建议按下面顺序排查：

1. 看 [../main.py](../main.py) 是否在调用 bootstrap 前就抛错
2. 看 [../app_渠系计算前端/bootstrap.py](../app_渠系计算前端/bootstrap.py) 是否已执行 `ensure_safe_windows_platform_queries()`，避免 `pandas` 等第三方库触发阻塞式 WMI 查询
3. 看 [../app_渠系计算前端/bootstrap.py](../app_渠系计算前端/bootstrap.py) 是否在授权校验阶段退出
4. 看 `tools/qt_webengine_doctor.py` 与 `webengine_diagnostics.py` 是否确认标准 WebEngine 被系统环境拦截
5. 看 [../app_渠系计算前端/app.py](../app_渠系计算前端/app.py) 的 UI 装配是否因为某个面板工厂导入失败中断
6. 看 [../app_渠系计算前端/project_manager.py](../app_渠系计算前端/project_manager.py) 是否因保存/恢复逻辑抛出连锁异常
7. 看是否由更新命令行参数触发了特殊更新分支
8. 在普通 Windows 桌面权限下按进程枚举可见窗口，确认标题、窗口矩形和持续响应；不要把受限诊断进程看不到高完整性窗口误判为程序未启动
