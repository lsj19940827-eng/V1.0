# 发版与自动更新指南（正式清单 + 双下载源）

## 当前实现同步说明（2026-05-10）

- 应用内更新已改为“主程序下载 + 独立更新助手安装”模式；点击“立即安装更新”后，不再弹出 `cmd` / PowerShell 黑窗。
- 安装阶段改为独立品牌化窗口，按“准备安装 / 等待主程序退出 / 校验安装环境 / 备份当前版本 / 解压并应用更新 / 清理临时文件 / 安装完成”展示阶段进度。
- 安装进入“校验安装环境”后，会继续显示细分状态，例如“正在清理上次失败残留”“正在检查写入权限”“正在统计安装目录大小”“正在解压完整安装包或补丁包”“正在校验补丁适用性（x/y）”；如果正在校验大文件哈希，还会显示单文件百分比，避免用户误以为窗口卡死。
- 下载完成后会先校验更新包 checksum，再进入安装；补丁应用完成后还会按 `target_files` 再做一次目标版本验收，避免“包看起来下完了，但内容不完整”或“补丁应用了一半还被当成功”。
- `siphon_autosave.json`、`data/autosave/` 和 `*_autosave.qxproj` 这类运行时文件，已从 manifest、patch diff 和补丁严格哈希校验里排除；全量安装成功后也会保留，不再把用户自动保存数据当成程序文件覆盖掉。
- 安装开始时会自动清理当前会话之外的旧 `_update_sessions` 残留，避免上次失败留下的临时目录继续拖住后续更新。
- 安装前会强制检查三项前置条件：
  - 当前项目不能有未保存修改；如果更新包已下载且项目未保存，更新窗口会提示“保存并继续安装”，保存成功后直接复用已下载包继续安装。
  - 当前安装目录必须可写；不再走管理员提权。
  - 当前磁盘剩余空间必须满足“解压 + 回滚备份”最低要求。
- 安装失败时会明确区分三种回滚结果：`无需回滚 / 已成功回滚 / 回滚失败`，并在失败页提供“查看日志 / 打开更新目录 / 重新下载后再试”入口。
- 安装成功后不再自动重启主程序，而是停留在成功页，由用户点击“启动新版本”进入新版。
- 发布包中现在必须包含独立更新助手 `CanalHydraulicCalcUpdater.exe`；构建脚本会自动一并产出。
- 更新助手在安装进行中禁止关闭，避免中断安装或回滚；只有成功页和失败页允许关闭。
- 如果补丁包版本范围不匹配，或本机文件状态与补丁预期不一致，安装助手会自动改用完整安装包继续更新。
- 通用补丁现在只面向近版本链路，当前默认最低覆盖版本是 `1.3.0`；更老版本会直接下载全量包。
- 构建、正式发版、发版 GUI 和回补 patch 如果发现补丁删除文件过多、总覆盖量过大，或补丁包接近完整包，会直接跳过补丁发布，只保留全量包。
- 正式发版后会自动写入 `.release-snapshots/` 快照，固定 `tag / full zip / patch zip / manifest / version.json` 的对应关系；后续回补 patch 只能基于这份快照。
- 正式 `version.json` 仍由 GitHub Gist 提供；完整包只上传 GitHub Release，不再上传 Gitee。
- 补丁包只有在不超过 100MB 时才上传 Gitee Release，并把 Gitee 附件地址写入 `patch_url_mirrors`；超过 100MB 时自动跳过 Gitee，不阻断正式发版。
- 客户端下载补丁时先使用现有 GitHub/代理地址，失败或 SHA256 校验不通过时再尝试 Gitee 镜像地址；补丁失败后回退全量包时使用 GitHub 完整包地址。
- 正式发版开始前会同时检查 `GITHUB_TOKEN` 与 `GITEE_TOKEN`，缺少 Gitee 令牌时直接停止，避免只发布到 GitHub 而 Gitee 未同步。
- 已发正式版如需单独补挂 patch，必须基于这份快照执行 `tools/backfill_patch_release.py`；如需临时撤 patch，则执行 `tools/disable_patch_release.py`。
- 构建阶段现在还会先校验 Word 导出依赖 `python-docx / latex2mathml / lxml`；缺失时直接终止打包，并提示执行 `pip install python-docx latex2mathml lxml`。
- 构建主程序和更新助手时会自动排除 Codex 自带 PDF/图片运行时注入的原生 DLL 路径，避免把 Poppler ICU、libheif UCRT 等宿主依赖混入正式包；最终 ZIP 仍需重新解压，并在仅保留 Windows 系统目录的精简 `PATH` 下通过启动冒烟。
- 失败页不再直接展示技术异常，面向用户只显示可操作文案；详细异常继续写入安装日志。

> 更新日期：2026-05-10  
> 当前实现：仅保留正式 Release + 正式 Gist 主入口；完整包走 GitHub，100MB 以内补丁包可走 GitHub/Gitee 双下载源，用户端不再提供预发布切换入口。

## 一、当前实现同步说明

- 自动更新仅检查正式 `version.json`，启动时静默检查和手动“检查更新”都走同一正式源。
- 正式源里的旧字段保持不变，新客户端会额外读取 `patch_url_mirrors` 作为补丁备用下载地址。
- 检查更新弹窗不再向用户暴露“测试（预发布）”通道。
- 如果本机安装过高于正式版的内部构建，正式通道仍保留“降级安装正式版”的兼容入口。
- 发版脚本 `tools/release.py` 只支持正式发布，不再支持 `--prerelease`、`--gist-target test` 或双 Gist 分流；完整包只上传 GitHub Release，100MB 以内补丁包才同步到 Gitee Release。

## 二、发布通道规则

| 项目 | 当前规则 |
|------|----------|
| 允许发布分支 | `master` |
| Release 资产 | GitHub Release 完整包；100MB 以内补丁包可同步到 Gitee Release |
| 更新清单 | 正式 Gist `version.json` |
| 用户更新入口 | 仅正式通道 |

硬规则：

1. 非 `master` 分支禁止执行正式发版。
2. 发版脚本只写正式 Gist，不再维护测试 Gist；Gitee 只作为同一正式版本的补丁包镜像，不作为第二套清单，也不承载完整包。
3. 缺少 `GITEE_TOKEN` 时正式发版必须提前停止。
4. 发布前必须确认工作区没有无关产物被一并 `git add -A`。

## 三、正式发版

```bash
git checkout master
git pull origin master

python tools/release.py patch
python tools/release.py minor
python tools/release.py major

python tools/release.py patch -m "- 修复水面线问题\n- 优化更新提示"
python tools/release.py patch --no-bump --tag-suffix rc.20260317.1
```

说明：

- `--no-bump` 仅表示跳过 `version.py` 递增，保留当前版本号继续发版。
- `--tag-suffix` 用于给 tag 增加后缀，例如 `v1.1.1-rc.20260317.1`。
- 发版脚本会自动执行：版本处理、打包、`git add -A`、`commit/tag/push`、创建 GitHub 正式 Release、上传全量包，并在补丁覆盖范围安全且补丁明显小于完整包时一并上传补丁包、更新正式 Gist、写入 `.release-snapshots/` 发布快照。补丁包不超过 100MB 时才额外上传 Gitee；完整包永远不上传 Gitee。
- 正式打包会先经过 `tools/build.py` 的分组依赖校验，并隔离 Codex 宿主注入的原生依赖路径；如果 Word 导出依赖不完整，会在进入 PyInstaller 前直接失败，不再继续发布。
- 如需临时撤下当前高风险 patch，只改 Gist patch 字段，使用 `D:\V1.0\.venv\Scripts\python.exe tools/disable_patch_release.py --version <版本号>`。
- 如需事后回补 patch，必须基于正式快照执行 `D:\V1.0\.venv\Scripts\python.exe tools/backfill_patch_release.py --version <目标版本> --min-version 1.3.0`，不再允许拿漂移过的本地 `dist` 或手工改过的 manifest 直接回补。

### 已发正式版回补 patch

当正式版已经发出，但需要单独补挂一个近版本 patch 时，不重走完整发版，改用：

```bash
python tools/backfill_patch_release.py --version 1.3.4 --min-version 1.3.0
```

说明：

- 这个脚本不会重建 tag，也不会重传全量包。
- 它会从 `.release-snapshots/` 中读取目标版本，以及 `--min-version` 到目标版本前的全部正式快照，只使用快照里固化的 manifest、version.json 和全量包。
- 如果快照里记录的本地全量包已不存在，脚本会按快照中的下载地址重新拉取，并先校验 SHA256 再继续。
- 如果现有 Release 下已经有同名 patch 资产，会先删掉旧资产再上传新的；但补丁接近完整包或覆盖范围过大时会直接停止回补，不会上传也不会改 Gist。
- 它只给 Gist `version.json` 补齐 `patch_url / patch_size_mb / patch_sha256 / min_patch_version / patch_base_version` 等补丁字段，不改已有全量包字段。
- 为避免补错版本，脚本会先检查 Gist 当前 `latest_version` 是否仍等于目标版本；不一致时会直接停止。

## 四、手动更新体验

- 程序启动后会后台静默检查正式更新源。
- 点击侧边栏“检查更新”会打开详情弹窗，但不再显示“更新通道”下拉。
- 发现新版本时，只有 `min_patch_version` 范围内的近版本才会优先提示补丁包；更老版本会直接提示全量包。
- 补丁下载时会先走现有 GitHub/代理地址，失败或 checksum 不一致时自动尝试 Gitee 镜像地址。
- 补丁下载失败或补丁安装不适用时，会自动回退到全量包；全量包使用 GitHub 下载地址。
- 更新包下载完成后，如果当前项目还有未保存修改，点击安装会先提示保存并继续；保存成功后不会重新下载安装包。
- 无论补丁还是全量包，安装窗口在“校验安装环境”阶段都会继续显示细分动作；其中全量包现在也会显示“统计安装目录大小 / 解压完整安装包”的状态，补丁大文件哈希会显示单文件百分比。
- 如果用户机器上还留有上次失败的 `_update_sessions` 目录，安装前会先自动清理；清理失败时，窗口会直接提示先关闭软件，仍失败再重启电脑后再试。
- 如果安装目录里已有自动保存文件、license 或其它运行时用户数据，成功安装后会继续保留，不会被新包覆盖。
- 当前本机版本高于正式版时，可在正式通道执行降级安装。

## 五、`version.json` 字段

| 字段 | 说明 |
|------|------|
| `latest_version` | 最新正式版本号 |
| `download_url` | 全量包下载地址 |
| `download_url_mirrors` | 全量包备用下载地址列表，可选；当前不写入 Gitee 地址 |
| `download_sha256` | 全量包 SHA256 |
| `patch_url` | 补丁包下载地址，可选 |
| `patch_url_mirrors` | 补丁包备用下载地址列表，可选 |
| `patch_sha256` | 补丁包 SHA256，可选 |
| `changelog` | 更新日志 |
| `release_date` | 发布日期 |
| `min_version` | 最低兼容版本 |
| `min_patch_version` | 补丁最低覆盖版本；当前默认只给 `1.3.0+` 提供补丁 |
| `file_size_mb` | 全量包大小 |
| `patch_size_mb` | 补丁包大小，可选 |
| `channel` | 固定为 `stable` |

## 六、首次配置

1. 创建 GitHub Token，并勾选 `repo` 与 `gist` 权限。
2. 创建 Gitee 私人令牌，并确保具备当前仓库 Release 创建与附件上传权限。
3. 在项目根目录创建 `.env`：

```env
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
GITEE_TOKEN=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

4. 在 `repo_config.py` 中配置正式 Gist 的 `GIST_ID`，并维护 Gitee 仓库与 API 基本信息。

## 七、故障排查

- `tools/release.py` 报“只有 master 允许执行正式发版”：
  当前分支不是 `master`，请切换分支后重试。
- 用户端检查更新失败：
  优先检查网络、Gist 可访问性以及防火墙限制。
- 发版前提示缺少 `GITEE_TOKEN`：
  在项目 `.env` 或系统环境变量里补充 Gitee 私人令牌后再重新发版。
- GitHub 地址可下载但 Gitee 镜像失败：
  先确认补丁包是否小于等于 100MB、Gitee Release 附件是否存在，再核对 `version.json` 的 `patch_url_mirrors` 是否指向同一版本；最终是否可安装仍以 SHA256 校验为准。
- 补丁没有出现在正式发布里：
  先看本次构建、正式发版或回补流程是否命中了“覆盖范围过大 / 补丁包接近完整包”的兜底规则；命中后会只发布全量包，这是当前的预期行为。
- 需要回补 patch：
  只能用 `.release-snapshots/` 里的正式快照执行 `tools/backfill_patch_release.py`；如果快照缺失或快照资产校验失败，应先补齐快照，不要直接拿本地 `dist` 回补。
- 用户反馈一直卡在“校验安装环境”：
  先看安装窗口是否已进入“正在清理上次失败残留 / 正在校验更新包完整性 / 正在检查写入权限 / 正在统计安装目录大小 / 正在解压完整安装包或补丁包”等细分状态；如果提示旧残留清不掉，先完全退出主程序和更新助手，仍失败再重启电脑后重试。
- 用户反馈“补丁不适用”但本机明明只是正常用过：
  先确认线上 patch 是否仍包含运行时自动保存文件；当前规则下这些文件已排除出补丁严格哈希校验，若线上仍出现旧行为，优先考虑临时执行 `tools/disable_patch_release.py`，先只保留全量包更新。
- 用户反馈版本高于正式版：
  这是历史内部构建兼容场景，可在正式通道使用降级安装回到正式版。
